# 恢复与服务器部署

本仓库已基于上游 main `24c80bf8540f511513762a9015fcd73ebcd02fec`（2026-08-31）升级到 `https://www.douyin.com/chat`。dev 已合入该主线；api 是另一套旧测试方案。

目前优先选择固定服务器 Docker 部署。上游仍未承诺长期稳定，首次运行应以抖音聊天中的实际收信为验收标准。

## 1. 首次部署

在 Ubuntu 24.04、已安装 Docker Compose 的服务器上，进入本项目目录。复制 `.env.example` 为 `config/.env`，填写 TASKS、消息模板及每天运行时间。所有 Cookie 仅存放在 `config/` 内；不要提交到 GitHub。

```bash
mkdir -p config logs
chmod 700 config
cp .env.example config/.env
chmod 600 config/.env
docker compose build
```

如使用本文的扫码辅助，可先从配置中移除示例 `COOKIES_...` 行；扫码后会自动保存正确的 Cookie。

## 2. 在实际服务器上扫码登录

先关闭定时容器，避免登录或调试时同时发消息：

```bash
docker compose stop douyin-spark-flow
docker compose -f docker-compose.login.yml --profile login build
docker compose -f docker-compose.login.yml --profile login up -d
```

在自己的电脑开一个终端，使用你已有的 SSH 连接：

```bash
ssh -N -L 127.0.0.1:18765:127.0.0.1:6080 你的SSH别名
```

终端保持运行，在浏览器打开 `http://127.0.0.1:18765/vnc.html?autoconnect=1&resize=scale`。里面是服务器上的 Chromium。使用需要续火花的抖音账号扫码，在手机上确认登录；如有验证码，由本人完成。

程序只有在检测到登录 Cookie 和聊天会话列表后才保存配置。查看：

```bash
docker compose -f docker-compose.login.yml --profile login logs --tail=30
sudo cat config/login-ready.json
```

`login-ready.json` 仅包含保存状态和时间，不包含 Cookie。它证明登录状态已被保存，不证明消息已送达。请核对时间是刚才这次登录。

登录窗口最多维持 15 分钟。超时或需要换号时重新执行 `up -d --force-recreate`。扫码后关闭辅助容器：

```bash
docker compose -f docker-compose.login.yml --profile login down
```

此入口只绑定服务器的 `127.0.0.1:6080`；不需要开放云安全组端口，不要改成公网监听。

## 3. 首次验证与启用定时

构建后先验证 cron 的最小环境能够启动镜像内浏览器（仅打开空白页，不登录、不发送）：

```bash
docker compose run --rm --entrypoint env douyin-spark-flow -i PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin HOME=/root LOGNAME=root SHELL=/bin/bash python /app/docker/browser-check.py
```

Docker 入口会在环境变量缺失时恢复 `/ms-playwright` 浏览器路径。仅验证文件存在或手动容器启动成功，不能替代定时环境检查。

先检查配置而不发送消息：

```bash
docker compose run --rm --entrypoint python douyin-spark-flow /app/docker/runtime.py validate
```

运行前确认 `TASKS` 内目标；一次运行会向这些目标提交配置的消息。建议先只选择一个已确认目标，并在手机聊天中核对实际收信，再恢复完整列表。手动执行一次（实际发送）：

```bash
docker compose run --rm --entrypoint /app/docker/run-task.sh douyin-spark-flow
```

手动与定时任务共用文件锁；另一轮正在运行时退出码为 75，不会重复启动。

配置 `TZ=Asia/Shanghai`、`CRON_HOUR=9`、`CRON_MINUTE=0`、`CRON_SECOND=0` 表示每天北京时间 09:00。首次验证通过后启动：

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=80
```

配置改动后执行 `docker compose restart`。应用日志在 `logs/app.log`；任务出现错误会非零退出，并在容器输出留下错误。逐好友结果保存在 `logs/last-run.json`，可按下面方法接入微信通知。

### 当天部分失败后的补跑

核对 `logs/last-run.json` 后，使用下面的入口继续当天未提交的目标：

```bash
docker compose exec -T douyin-spark-flow /app/docker/run-task.sh --resume
```

补跑要求账号、好友名单与原记录完全一致，而且原任务是配置时区的当天。已提交、按发送键后结果未知、消息输入出错或已有草稿的对象不会自动重发；仅补跑未尝试、未找到和明确在会话打开阶段失败的目标。补跑前保留 `logs/before-resume-*.json` 私有快照，微信通知包含合并后的全部结果。不要删除原报告再补跑。

单轮运行中，会话打开失败先记录并继续其他目标，再为未输入消息的目标重建浏览器上下文，最多尝试 `TASK_RETRY_TIMES` 轮（上限 3）。每次输入前和发送前检查当前会话标题；按 Enter 后出现异常仍停止，不自动重发。

### 小内存服务器

Chromium 的页面可能在没有触发 OOM 时因内存回收而停顿。可用 `free -h`、`cat /proc/pressure/memory`、`docker stats --no-stream` 和 `swapon --show` 检查；不能仅凭 `OOMKilled=false` 排除内存压力。约 2GB 内存的服务器建议准备 2GB Swap 缓冲、保留充足磁盘空间，并关闭不用的登录辅助浏览器；同时确认 `vm.swappiness` 不是 0（本服务器设置为 60）。Compose 保留 850MB RAM 限额，允许最多 1700MB RAM 与 Swap 合计；系统没有 Swap 时此配置不会创建 Swap。若仍频繁出现内存压力，应增加服务器内存。

### PushPlus 微信任务结果通知

此功能接入 Docker 的任务入口：每次运行结束发一条汇总，成功提交和失败都会通知。`NOTIFY_PROVIDER=off` 为默认值；开启时填 `NOTIFY_PROVIDER=pushplus` 和 `PUSHPLUS_TOKEN`。使用 PushPlus 用户 Token 或消息 Token，仅给你本人推送，不配置群组或好友令牌。

在服务器终端执行以下命令，隐藏输入 Token，保存后发送一条明确标为测试的微信通知；不会运行抖音任务：

```bash
docker run --rm -it -v "$PWD/config:/config" --entrypoint python douyinsparkflow:local /app/docker/configure-notify.py --test
```

确认微信收到测试。如果原本已在运行定时容器，保存后执行 `docker compose restart`；首次部署仍需先确认好友和实际收信，再启用定时。

通知列出已提交、提交失败、未找到、未尝试和状态未知的对象，包含备注（来自最近一次好友核对）与配置 ID。已提交只表示按过发送键，不能证明抖音实际送达。若 Enter 操作异常，归为“状态未知”，不会自动重发。

`last-run.json` 的 `notification.status=accepted` 只表示 PushPlus 接收了请求，不保证微信已显示；推送失败会记录安全的错误类别，且不会重新执行抖音任务。服务器停机、进程被强制终止或完全断网时，任务自身无法可靠发送失败通知。

接口依据：[PushPlus 官方消息接口](https://www.pushplus.plus/doc/guide/api.html)。Token、Cookie 和好友核对报告不会提交到 GitHub。

### 添加或删除续火花对象

修改 `config/.env` 中 `TASKS` 的 `targets` 数组，保留其他账号字段。每个对象必须是带双引号的字符串，数字抖音号也一样。优先填写抖音号，也支持完整昵称或备注；只改名单无需重新扫码。

程序只匹配网页版的已有会话，不会自动加好友或搜索陌生人。新增前先在抖音建立会话，并确认网页版列表可见。遇到相同昵称或备注，建议设置不同备注并核对首次收件人。修改后先执行上面的配置验证，再重启容器。

登录后可只读核对已配置对象对应的昵称、备注和抖音号，不打开会话或发送消息：

```bash
docker compose run --rm --entrypoint python douyin-spark-flow /app/docker/audit-targets.py
sudo cat logs/target-audit.json
```

报告只包含配置对象；`missing` 表示本次未匹配，不能据此判断已删除好友。`ambiguous` 或 `sender_title_collision: true` 需要人工核对重名。`scan_complete: false` 表示本次未完整遍历；若 `identity_responses_received` 为 0，应排查身份接口变化。

## 4. 常见故障

| 现象 | 处理 |
|---|---|
| 缺少 COOKIES_... | 执行服务器扫码登录，或导入从聊天页导出的完整 Cookie JSON。 |
| 聊天页面元素加载超时 | 在登录辅助确认登录和验证状态；若网页手动聊天正常，再检查页面结构变化。 |
| 部分目标未提交消息 | 检查目标在网页会话列表中是否可见，以及备注、昵称或抖音号是否匹配；不要立即重跑全部目标。 |
| 已按发送键但手机未收到 | 本项目未验证服务端送达；先排查网页掉线、消息限制等，不要用反复发送代替诊断。 |
| GitHub Action required | 属于 GitHub 的运行审批拦截；切换分支和更新 Cookie 不会自动解除。 |

## 5. GitHub Actions 备用

本次移除引用不存在分支的 dev/api 两条工作流，并移除 keepalive。主流程保留手动触发；定时任务只有在仓库变量 `ENABLE_GITHUB_SCHEDULE=true` 时才执行。服务器定时运行时请保持 GitHub 备用工作流关闭，以免重复发消息。

如将来改用 GitHub：启用主工作流，继续在 `user-data` 环境配置 TASKS、消息模板和 COOKIES_...，审核工作流后处理 GitHub 的审批提示，再手动测试。只有实际收信确认后才开启 `ENABLE_GITHUB_SCHEDULE`。GitHub 的执行机器和 IP 可能变化，仍可能被抖音要求重新登录；本次不保证解除该限制。
