## 2026-09-14：会话超时恢复与当天断点补跑

09:00 的任务成功启动并提交 13 个目标，随后在另一目标等待聊天输入框 120 秒超时，另外 13 个目标未执行。保存的登录有效，旧输入框类名仍存在；只读诊断复现了会话点击超时，随后同一会话正常加载，也没有观察到限制提示。

服务器实际内存约 1.6GB、没有 Swap。诊断时主机内存 PSI full 的 10 秒均值达到 39.62%，浏览器容器内为 35.96%，而 cgroup 的 oom/oom_kill 计数为 0。证据表明没有 OOM 也可能因内存回收严重停顿；09:00 当时没有保存 PSI 采样，因此不将其宣称为已捕获的唯一原因。该服务器已配置 2GB Swap 并持久化，原 fstab 留有备份。Compose 的 RAM 限额仍为 850MB，RAM 与 Swap 合计上限明确为 1700MB。

脚本改为按准确会话标题重新定位，避免复用会话列表重排前的位置；等待会话标题和真实 contenteditable 输入区就绪，输入前检查已有草稿，发送前再次核对标题。会话准备失败先继续其他目标，再重建上下文仅重试尚未输入的目标，最多 3 轮。账号身份映射每个上下文重置，滚动等待使用 Playwright 事件等待。

新增 `run-task.sh --resume`：仅同一天、完全相同的账号和目标集合可以补跑。原报告先保存私有快照；保留已提交和不确定结果，不重发消息输入失败或已有草稿的对象。任务和微信通知按全体目标合并结果，通知明确标注断点补跑。Cookie、Token、实际名单、服务器运行报告仍不进入仓库。

第一次修复后的补跑在输入框提示属性动态变化处再次遇到超时，已将输入区定位收紧为 Slate 编辑器的稳定属性 `contenteditable=true` + `data-slate-editor=true`，不再依赖会在输入后消失的 `data-placeholder`。第二次补跑于 11:16—11:18（北京时间）完成：14 个剩余目标全部提交；合并原先 13 个结果后，27/27 均为 `submitted_unverified`，退出码 0，PushPlus 接受汇总通知。服务器 Swap 已实际使用约 446MB，内存 PSI full 降至约 0.24%（10 秒均值）；`vm.swappiness=60` 已写入 `/etc/sysctl.d/99-douyinsparkflow-memory.conf`。本轮只在抖音端观察到按发送键，不把该状态当成收件方实收证明。

## 2026-09-13：修复定时环境找不到浏览器

09:00 的定时任务触发后，在浏览器启动阶段失败，所有配置目标均为 `not_attempted`。Chromium 已安装在镜像的 `/ms-playwright`；问题是 cron 没有继承镜像的 `PLAYWRIGHT_BROWSERS_PATH`，Playwright 转而查找 `/root/.cache/ms-playwright`。前一天的手动容器运行验证没有覆盖这个环境差异。

改动：Docker 配置加载时，浏览器路径缺失或为空则恢复为 `/ms-playwright`，保留明确设置的自定义路径。浏览器启动失败现在保留原始异常、清理 Playwright，并向结果报告传递明确的浏览器故障原因，不再返回 `None` 后产生二次解包错误。

新增 `docker/browser-check.py`，只启动空白页、不载入登录状态或发送消息。57 项测试已在本机和 Linux Docker 内通过，并通过清空镜像环境变量后的实际浏览器启动检查。该检查覆盖了本次遗漏的启动条件。

真实 cron 于北京时间 09:14 触发补跑，09:17 完成：27 个目标均记录为 `submitted_unverified`，失败、未找到和结果未知均为 0，退出码为 0；PushPlus 接受了结果汇总。保存的登录状态仍有效，没有重新扫码。本次记录仍不等同于逐个收件方已确认实收。

临时补跑使用与日常任务相同的入口和定时环境，设有只执行一次的标记，已在触发后移除临时定时项。原失败和恢复结果报告均留存；本次仅在确认所有目标均未尝试后补跑。每天北京时间 09:00 的正式任务继续保留。

浏览器路径依据：[Playwright 浏览器文件管理](https://playwright.dev/python/docs/browsers#managing-browser-binaries)。

### 已实现的改动

| 范围 | 改动与结果 |
|---|---|
| GitHub Actions | 移除引用不存在分支的 api/dev 工作流和 keepalive；保留主工作流手动运行，定时运行需显式设置 `ENABLE_GITHUB_SCHEDULE=true`，便于避免与服务器重复调度。同时收紧权限并固定外部 Action 版本。 |
| Docker 运行 | 在 Ubuntu 24.04 上构建并验证运行镜像，使用镜像内置 Chromium。默认每天 `Asia/Shanghai` 时间 09:00 执行；启动容器只启动调度，不立即发送。手动与定时入口共用 `flock` 文件锁，防止并发运行。 |
| 配置与 Cookie | 启动浏览器前校验账号、目标和 Cookie。修复配置写入的转义与变量插值问题，允许保留浏览器导出的空名称 Cookie，继续检查值和域名等必要字段。 |
| 扫码登录 | 增加服务器 Chromium 登录辅助，经本机 SSH 隧道访问；入口只监听服务器回环地址。检测到登录 Cookie 和聊天列表后，原子保存 Cookie 及不含凭据的完成标记。后续复用保存状态，失效或被要求验证时再登录，没有设定每天强制扫码。 |
| 好友核对 | 增加只读核对入口，读取身份响应并遍历列表，不打开会话、不发送消息。对配置目标报告匹配、未匹配、身份歧义、重名风险和遍历是否完成，供增删名单前核对。 |
| 空备注匹配 | 修复身份接口返回空备注时无法按昵称关联抖音号的问题；等待页面时处理网络回调，减少身份信息尚未入表造成的漏匹配。 |
| 逐好友结果 | 保存 `logs/last-run.json`，分别记录已提交、失败、未找到、未尝试和状态未知。后续目标失败不会覆盖前面已提交的状态；按 Enter 前先持久化“提交中”，Enter 异常则标为结果不确定并停止，不自动重发。 |
| 微信通知 | Docker 任务正常或异常结束时，仅尝试发送一条 PushPlus 汇总，列出各目标结果及可识别的失败原因。推送失败单独记录，不改变抖音任务结果，也不重新执行发送。 |
| 私人数据 | Cookie、Token、实际配置、好友核对报告和运行日志不入库、不打入镜像；配置文件使用受限权限。公开代码和日志说明不包含私人昵称、好友名单或消息内容。 |

PushPlus 使用官方消息接口的微信渠道。通知中的“已提交”只表示脚本按过发送键，**不表示抖音已送达**；PushPlus 返回接受状态也不表示微信已经显示。接口超时不自动重试；服务器停机或进程被强制终止时，任务自身无法保证发出通知。[PushPlus 官方接口文档](https://www.pushplus.plus/doc/guide/api.html)
